# Redis command deadlines — WP4

Runtime uses Upstash TCP/TLS. `REDIS_COMMAND_TIMEOUT_MS` defaults to 1000 ms and must be an integer from 1 to 5000 ms. It is distinct from `REDIS_CONNECT_TIMEOUT_MS` (connection startup). The node-redis per-command timeout removes timed-out commands from the client queue; it does not guarantee that an already sent command did not execute on the server. Do not use timeout as proof a mutation was rolled back.

24/11 update: a loopback TCP proxy proved that node-redis's native timeout does not bound replies after the command is written. The application now also enforces a reply deadline for command-client GET/MGET, rate limit, cache writes/index/locks, provider/member location reads and writes, tracking reads/writes and notification publish. On an expired reply it destroys the ambiguous socket and reconnects, without retrying the command. Shutdown destroys open Redis sockets to avoid waiting forever on a half-open reply. The separate subscriber socket also bounds subscribe/unsubscribe acknowledgements and reconnects after a half-open reply. The local Redis fault suite passed 9/9, including RED/GREEN tests for stalled location mutations, discovery, tracking, cache/index/lock operations and subscriber acknowledgement. Upstash slow/half-open behavior and p95/p99 remain unmeasured.

| Path | Deadline and current fallback | Required behavior |
| --- | --- | --- |
| Generic GET/MGET cache | Per-command deadline, 1000 ms by default; returns miss on error/timeout. | Fail open only for data already safe to rebuild from PostgreSQL. |
| Global rate limit | Atomic Lua command with per-command deadline, 1000 ms by default; timeout and transport errors report 503 for protected requests. Public Feed reads use a 100 ms native command deadline and retain their existing 100 ms outer fallback budget. | Fail closed on protected writes; no fallback to an unshared limit. A server-side increment can finish after a client timeout. |
| Cache writes, lock and index rebuild | SET, batch SET/DEL, lock acquire/release, index replace/read, generation advance and DEL have an application reply deadline. Cache operations retain their existing miss/false/null/void fallback. | A timed-out mutation may have applied. The lock token and generation ordering remain necessary to make retries safe. |
| OTP and account security | No new Redis deadline in this increment; inspect the actual storage path before altering auth behavior. | No fail-open for authentication, OTP or access control. |
| GPS, location, tracking and SSE Pub/Sub | Command-client provider/member location and tracking operations have application reply deadlines. Publish is bounded. Subscribe/unsubscribe acknowledgements have a separate reply deadline. A local two-client reconnect/cleanup test and half-open acknowledgement recovery test pass. | Fail closed where location freshness or ordering matters; test Upstash reconnect/subscriber lifecycle under cloud latency and repeated faults. |

`data.redis.commands.read`, `.batchRead` and `.rateLimit` expose `timeouts`, `errors` and durations as fixed groups in the process-local admin snapshot. A timeout increments both `timeouts` and `errors`. Connection startup timeouts remain under `data.redis.connections.*.timeouts`. Cache failure warnings are limited to one per operation per 30 seconds per process; counters are never sampled. Values, keys, URLs and exception text are not logged by this instrumentation.

`data.redis.cacheLookups` counts individual GET/MGET results for categories, services, Feed posts and other keys. An absent or malformed JSON result counts as a miss; a timeout/disconnect counts as an error for every attempted key. Disabled Redis does not record lookups. Feed post validation can still reject a JSON cache hit at the application layer; use the Feed service's separate counters for effective Feed cache hits.

Before changing the production timeout budget, test an isolated Upstash database under slow, disconnected, half-open and recovering connections. The loopback fault suite proves that command-client and subscriber requests complete within their local deadlines and recover; it does not establish cloud latency or server-side cancellation. Tune the default with measured Upstash p95/p99 and rate-limit error budget.
